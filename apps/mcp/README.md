# ChatGPT Computer Plugin

Thin MCP adapter for `heidi-dang/computer`. CPTR remains responsible for execution, persistence, authentication, autonomous supervision, verification, retries, approvals, and restart recovery. This repository only exposes the ChatGPT-facing MCP tools and forwards scoped requests to CPTR's `/api/control/v1` API.

Task and autonomous creation results hydrate an inline MCP Apps Live Workbench. The widget is a view over CPTR's server-authoritative event stream; it does not run workers or replace the existing MCP tools. The MCP connection may end while CPTR continues the server-side autonomous monitor.

## Setup

```bash
npm install
cp .env.example .env
```

Set `CPTR_BASE_URL` to the CPTR origin and `CPTR_API_TOKEN` to a scoped CPTR bearer token. The CPTR token remains the execution and authorization boundary and is never sent to an MCP client.

For the Cloudflare Access Managed OAuth deployment, set `PUBLIC_ORIGIN`, `MCP_ALLOWED_ORIGINS`, `MCP_OAUTH_RESOURCE`, `CLOUDFLARE_ACCESS_ISSUER`, `CLOUDFLARE_ACCESS_AUDIENCE`, `CLOUDFLARE_ACCESS_JWKS_URI`, and `MCP_OAUTH_ALLOWED_EMAIL`. `PUBLIC_ORIGIN` is the public HTTPS origin without a path. `MCP_ALLOWED_ORIGINS` is a comma-separated explicit browser-origin allowlist supplied by the operator; no client origin is built in; both settings are required when `NODE_ENV=production`, and the service fails closed if either is omitted. The origin validates the signed `Cf-Access-Jwt-Assertion` header for issuer, audience, signature, expiration, not-before, subject, and the configured identity allowlist. `MCP_OAUTH_SCOPES` is an optional space- or comma-separated required-scope list; leave it empty when the selected Access provider does not include a scope claim in its origin assertion.

`MCP_ACCESS_TOKEN` remains an optional operator/rollback bearer for direct trusted smoke tests. It is not the ChatGPT-facing authentication path when Cloudflare OAuth is configured.

```bash
npm run build
npm test
npm run typecheck
npm run dev
```

The MCP endpoint is `http://${HOST}:${PORT}/mcp` and health is `/health`.

The `/mcp` endpoint requires a valid Cloudflare Access assertion in production, or the optional static bearer for trusted operator smoke tests. The public protected-resource metadata endpoint is `/.well-known/oauth-protected-resource`; `/health` remains available for liveness checks.

## Tools

CPTR Computer defaults to a source-verified **30-tool compact MCP contract**. Mixed Workbench, SSH, managed Chrome, delegated-task, and delegated-monitor capabilities are split into read and control tools so read/status operations advertise `readOnlyHint: true`, `destructiveHint: false`, and `openWorldHint: false`, while control tools retain conservative destructive/open-world annotations. A source-verified **63-core-tool / 69-registered-action** legacy fixture remains only inside the explicit in-process compatibility test harness; the production HTTP server has no environment toggle that can expose it. `package.json` is the canonical application version: MCP `serverInfo.version`, the MCP contract version, Update Center manifest, `/health` app version, deployed-contract verifier, and Workbench client metadata all derive from that one value. A future semantic-version bump therefore propagates across the plugin runtime without maintaining separate version literals. The direct workspace surface covers listing, reading, searching, writing, exact editing, directory creation, file move/delete, Git status, bounded local command start/status/cancel operations, compact interactive terminal control, and compact LSP discovery/request/lifecycle gateways backed by administrator-configured language servers. The compact contract exposes `cptr_ssh_read` for alias/status inspection and `cptr_ssh_control` for remote run/cancel operations through literal aliases configured for CPTR's execution identity without weakening the generic command policy. Managed Chrome is likewise split into `cptr_chrome_read` for status/snapshot inspection and `cptr_chrome_control` for navigation, interaction, screenshots, and scoped session closure; both remain backed by CPTR's isolated managed Chrome/CDP runtime and never attach to the user's normal Chrome profile. Legacy dedicated SSH and `cptr_chrome_browser` names remain regression-test fixtures only and are never runtime-selectable in production. `cptr_plugin_update` is the stable Update Center action: it reports the current release/changelog and verifies the live MCP contract after ChatGPT's host-controlled Refresh/review step. The compact contract provides opt-in delegation through `cptr_delegate_task_read`, `cptr_delegate_task_control`, `cptr_delegate_monitor_read`, and `cptr_delegate_monitor_control`; the older task/autonomous names remain regression-test fixtures only. **ChatGPT remains the default planner and executor for a user prompt**, chaining the scoped workspace/coding tools itself. CPTR model delegation is available only if the user explicitly asks for it, includes the literal `allow:delegate` marker in the delegated task or goal, and supplies a fully qualified `provider/model` or `agent:profile/model` value; CPTR never auto-selects or discovers a provider model for normal plugin work. The compact contract exposes `cptr_workbench_sessions_read` and `cptr_workbench_sessions_control` for owner-scoped durable session inspection/lifecycle. It also exposes `cptr_benchmark` for an owner-scoped standardized coding suite with server-owned randomized grading; benchmark scores are comparable only within the same suite/version, while observed real-work engineering telemetry remains explicitly non-comparable. Every compact action accepts bounded self-reported `client_model` attribution, which is consumed at the MCP boundary and never forwarded as business authorization; the eight older dedicated Workbench Session names remain regression-test fixtures only. The initial bounded workspace-tool set provides static project, tree, metadata, multi-file, symbol, test-discovery, dependency, package-script, and release-readiness inspection, plus one server-owned local test-profile runner. Those tools remain confined to one owned workspace and never accept arbitrary host paths or unrestricted shell commands. Task and autonomous creation accept an `execution_policy` that CPTR enforces server-side to deny file-write tools, command execution, network-capable tools/external commands, and package installation independently; monitor workers inherit the same policy. Control tasks default to local-only authority (`allow_network: false`, `allow_package_install: false`) unless the caller explicitly opts in. Production routes delegated workflows only through the compact task/monitor read-control gateways; legacy execute/monitor actions are retained solely for regression coverage.

Tool schemas are bounded with Zod and each tool declares read/write/destructive annotations. Annotations guide client behavior but do not replace CPTR authentication or authorization.

## Official MCP shape

The production ChatGPT-facing contract uses the official TypeScript MCP SDK, Streamable HTTP at `/mcp`, explicit input/output schemas, OAuth metadata, and tool annotations. It advertises exactly **30 compact tools plus one MCP Apps resource** at `ui://cptr/live-workbench.html`. Only `cptr_open_live_workbench` publishes `_meta.ui.resourceUri`; every other production tool remains data-only. The legacy 63-core-tool / 69-registered-action surface remains available only to the explicit in-process regression harness and cannot be enabled through production environment configuration.

## CPTR Live Workbench

`cptr_open_live_workbench` is the single optional UI-producing Workbench session bootstrap. Ordinary ChatGPT Direct Coding must not call it as an activation step or prerequisite: ChatGPT should begin with the workspace, FDX, code, Git, test, SSH, or browser tool that directly matches the user's request. Use the opener when the user requests/resumes the Workbench, when a visible Apps UI is useful for the explicitly invoked Heidi/CPTR workflow, or for the explicit `allow:delegate` authorization path. It mounts `ui://cptr/live-workbench.html`; later tools remain data-only and update the existing Workbench through scoped activity/live metadata rather than producing additional widgets.

Live terminal UI streaming is **disabled by default** to prevent continuous SSE traffic, transcript re-renders, reconnect loops, ticket renewals, and host sizing churn from degrading the main ChatGPT conversation. The complete streaming implementation and endpoints remain available; operators can explicitly opt in by setting `CPTR_LIVE_TERMINAL_STREAMING=1` and restarting the plugin service. When streaming is disabled, prompt authorization still works normally, but the adapter does not retain prompt-terminal UI events or issue target live-stream tickets.

The initial open call returns one opaque prompt-terminal ticket in hidden `_meta` together with the server-selected streaming mode. The widget uses that ticket in an `Authorization` header with `/live/prompt/stream` and `/live/prompt/snapshot`. When a later CPTR operation has a durable task, monitor, or command target, the server appends a target-bound `live.bind` event to the prompt stream; the widget then consumes the existing target stream without receiving another UI-producing MCP result. Target stream tickets remain hidden from visible tool content and URLs. The target gateway forwards the private CPTR bearer server-side to:

```text
GET /api/control/v1/tasks/{task_id}/stream
GET /api/control/v1/autonomous/{monitor_id}/stream
```

CPTR persists bounded, redacted per-target events with monotonic sequences and sends an initial safe snapshot followed by replayable SSE. The widget reconnects with its last sequence, deduplicates events, and stops on terminal status. Tickets last 15 minutes, longer than the gateway’s bounded 10-minute stream interval; on an expired ticket the widget requests at most two fresh target-bound tickets and rebinds automatically. Slow streams are disconnected so they can reconnect and replay instead of growing memory without bound. The task and monitor streams intentionally omit prompts, raw output projections, and chain-of-thought from their snapshots; activity events are bounded and redacted before persistence.

The production Workbench is a bounded Apps SDK surface layered on the compact tool contract. It renders the CPTR overview, genuine redacted activity/terminal state, Direct Worker lanes, update status, and compact Stop/Copy/Pin/Expand controls. The overview is preloaded from hidden tool-result metadata and refreshes through the same-origin `/ui/overview` proxy with the short-lived Workbench prompt ticket; the browser never receives the CPTR service bearer. Evidence, review, steering, Git diff, and other control capabilities remain authoritative through MCP tools and durable CPTR APIs. The terminal keeps a bounded client transcript, follows new output only while the user is at the bottom, and preserves target/workspace isolation across rebinds.

A ChatGPT MCP Apps widget cannot attach arbitrary DOM directly to ChatGPT's composer or escape its host-managed widget surface. The terminal therefore uses CSS sticky positioning inside its allocated surface, and its user-triggered **Pin** action requests Apps SDK `pip` display mode when the host supports it. The host remains authoritative and may grant a different mode; on mobile, PiP may be coerced to fullscreen. No synthetic overlay is used.

Build the production tool server with:

```bash
npm run build
```

`npm run build` now compiles both the MCP server and the signed Workbench assets. `npm run build:ui` builds/copies only the Workbench surface; `npm run build:compat-ui` remains an alias for compatibility with older automation. Production sets `CPTR_WORKBENCH_UI=1`, `CPTR_HOT_RELOAD=0`, and leaves the legacy `CPTR_COMPAT_WORKBENCH=0` rollback flag disabled. Production therefore serves an inline/static Workbench resource with no external `resourceDomains`; its CSP `connectDomains` contains only the configured Heidi MCP origin. Development may enable hot reload explicitly. MCP tool/resource descriptor changes remain host-cached by ChatGPT and require the native connector Refresh/review path when the contract changes.

For local inspection, run `npx @modelcontextprotocol/inspector@latest`, select Streamable HTTP, and enter the configured `/mcp` URL. In ChatGPT Developer Mode, expose the endpoint through an HTTPS tunnel or deployment and add the `/mcp` URL as a connector. The Update Center publishes `/plugin/update`, emits best-effort MCP `tools/list_changed` notifications, and the Workbench probes the release manifest's verification action. If ChatGPT still has a frozen older snapshot, the Workbench shows **Update available**, the current release notes, and the native Refresh path; after Refresh, **Verify update** retries the host action and only reports success when ChatGPT can invoke the new contract. Validate `/health`: `app_version` and `mcp_contract.version` must equal the canonical `package.json` version; `workbench.enabled` and `workbench.ready` must be `true`; `workbench.hot_reload` must be `false`; `workbench.resource_uri` must equal `ui://cptr/live-workbench.html`; `mcp_contract.tool_count` must be `30`; and the release SHA must match the signed deployment commit. Then run `npm run check:deployed-contract` to verify exactly 30 tools, exactly one readable Apps resource, exactly one UI-producing tool, the production CSP, and release identity. ChatGPT's native app-action Refresh/review remains authoritative; the MCP server cannot bypass that host-controlled control.

## Security and limitations

- The CPTR token is read from the environment and is never returned in tool results or normalized errors.
- The direct-coding tools are not CPTR agent delegation. They are scoped CPTR workspace primitives that the official ChatGPT app may chain autonomously: list, read, search, write, exact edit, run command, inspect command output, and cancel command. They require no CPTR `model_id` and no external OpenAI API key.
- ChatGPT owns ordinary prompt execution. CPTR's task and monitor delegation tools reject delegated task/goal text without the literal `allow:delegate` marker, omitted model names, and bare connection/model identifiers that could trigger provider model discovery. An explicit delegation must include `allow:delegate` plus `provider/model` or `agent:profile/model` after the user asks for that model.
- Direct coding is confined to the selected owned workspace. It rejects absolute/traversal paths, environment files, binary/oversized reads, ambiguous edits, and destructive commands. A potentially external local command requires both explicit user approval through `allow_network=true` and CPTR’s separate `command:external` scope. Raw `ssh`, `scp`, and `rsync` remain forbidden through this generic endpoint even with network approval.
- Dedicated SSH execution requires `command:execute` plus `command:external`, accepts only literal aliases present in the execution identity's `~/.ssh/config`, invokes OpenSSH with an argv-based local process, uses non-interactive `BatchMode`, preserves normal host-key verification and known-host handling, bounds output through CPTR's existing command-session ring, and supports incremental status plus cancellation. SSH config values and private-key material are never returned by the host-discovery tool.
- Managed Chrome (`cptr_chrome_read` / `cptr_chrome_control` in production) requires `command:execute` and uses one CPTR-owned isolated Chrome profile/session per user/workspace. Only absolute HTTP/HTTPS navigation is accepted; embedded URL credentials and non-web schemes are rejected. Loopback navigation is permitted for local development/qualification, while non-loopback navigation additionally requires `allow_network=true` and `command:external`. Snapshots and typed values are bounded, typed input is not echoed back, and screenshots are confined to the selected workspace under `.cptr/screenshots/`.
- CPTR enforces workspace ownership and scopes such as `workspace:read`, `task:read`, `task:write`, `autonomous:run`, `git:read`, `coding:read`, `coding:write`, and `command:execute`. Existing tokens must be reissued with the three direct-coding scopes before these tools will work; `command:external` is intentionally not included in default newly issued keys.
- This adapter does not grant `git:write` or `deploy:write`.
- External/destructive autonomous assignments pause in CPTR with a durable approval record; production `cptr_delegate_monitor_control` approval only forwards the scoped decision and cannot bypass CPTR policy.
- The production Workbench is a bounded Apps SDK projection over server-authoritative CPTR/MCP state. It uses a short-lived Workbench ticket for browser refresh data, never exposes the CPTR service bearer, and does not expand the 30-tool action surface.
- Persisted workspaces whose host directories no longer exist are returned with `available: false` and rejected with a generic `workspace is unavailable` response; absolute host paths are redacted before any adapter error reaches ChatGPT.
- Browser CORS is origin-allowlisted through `MCP_ALLOWED_ORIGINS`; wildcard CORS is not used by the MCP or Live Workbench endpoints.
- CPTR inherits its host-level security model; do not expose it to untrusted users without an appropriate authentication and network boundary.
