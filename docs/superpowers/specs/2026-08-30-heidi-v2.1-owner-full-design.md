# Heidi v2.1 Owner-Full Workspace Bootstrap Design

## Goal

Make Heidi capable of starting from zero CPTR workspaces and taking an authenticated machine owner from a Git repository URL or existing directory to a ready ChatGPT Direct Coding workspace without manual terminal preparation. v2.1 also makes the highest-capability deployment profile explicit as `owner-full`, automatically warms FDX for Git repositories, and keeps the compact MCP contract coherent and testable.

## Security invariant

`owner-full` means maximum owner-authorized product capability, not anonymous or credential-blind remote control. CPTR authentication, Cloudflare/Managed OAuth, workspace ownership, secret redaction, path confinement for managed clones, and two-step filesystem deletion remain mandatory. Heidi must never expose raw control tokens, browser cookies, stored credentials, or secret files to ChatGPT.

The standard profile remains safe-by-default. Owner-full adds capabilities needed for explicit external execution and destructive workspace lifecycle operations, but irreversible deletion remains a confirmed two-step operation.

## Architecture

### 1. CPTR workspace lifecycle service

Create `cptr.services.workspace_provisioning.WorkspaceProvisioningService` as the single host-level provisioning boundary. It owns managed workspace-root resolution, destination-name validation, Git URL validation, clone/create/import operations, Workspace row registration, FDX warm-up, archive/unregister, and two-step managed-directory deletion.

Managed create/clone destinations live below `CPTR_WORKSPACE_ROOT`, defaulting to `<CPTR_DATA_DIR>/workspaces`. The service uses argv-based subprocess execution for Git, never shell interpolation. Repository URLs with embedded passwords/tokens are rejected. HTTPS, SSH URLs, and standard SCP-style Git SSH syntax are accepted.

`import` may register an existing absolute directory visible to the CPTR execution identity. It does not move or copy the directory. Filesystem deletion is allowed only for workspaces whose resolved path is inside the managed workspace root.

### 2. Versioned Control API

Add one lifecycle endpoint under `/api/control/v1/workspaces/lifecycle` accepting an action-discriminated request:

- `create` — create an empty managed workspace directory.
- `clone` — clone a Git repository into a managed workspace directory.
- `import` — register an existing directory as a workspace.
- `refresh` — re-run availability/Git/FDX readiness discovery for an existing workspace.
- `archive` — unregister the workspace but leave files intact.
- `request_delete` — return a short-lived confirmation ID for a managed workspace.
- `confirm_delete` — validate the confirmation ID, unregister the workspace, and remove its managed directory.

`create`, `clone`, `import`, and `refresh` require `workspace:provision`. `archive` requires `workspace:provision`. Delete actions require `workspace:delete`.

Responses use stable workspace IDs and never return absolute filesystem paths. Readiness includes `available`, `git_repository`, and bounded `fdx` status.

### 3. Automatic FDX readiness

After successful create/clone/import/refresh, Git repositories call the existing FDX intelligence `status` action using the same execution identity. FDX unavailability is non-fatal: the workspace is still returned as ready for normal CPTR Direct Coding with `fdx.status` indicating unavailable/degraded. This preserves CPTR as the authoritative fallback.

### 4. MCP compact workspace lifecycle tool

Add `cptr_workspace_lifecycle` to the compact public contract. ChatGPT can bootstrap a machine with no existing workspace because this action does not require a workspace ID for create/clone/import.

The compact workspace surface becomes:

- `cptr_workspaces` — read-only list/get.
- `cptr_workspace_lifecycle` — create/clone/import/refresh/archive/request-delete/confirm-delete.
- `cptr_workspace_inspect` — static repository inspection after a workspace exists.

The MCP client invalidates its workspace cache after successful lifecycle mutations so the newly created workspace is immediately discoverable.

### 5. Capability profiles

`bootstrap-control-token.py` supports:

- `standard`: existing Direct Coding scopes plus `workspace:provision`, allowing safe zero-workspace bootstrap.
- `owner-full`: all standard scopes plus `command:external` and `workspace:delete`.
- `full`: backward-compatible alias for `owner-full` during migration.

The installer UI calls the high-capability profile `owner-full` and maps persisted legacy `full` state to it.

Owner-full does not disable CPTR's destructive-command classifier or secret protections. Destructive filesystem lifecycle is performed through the purpose-built confirmed workspace API rather than an unrestricted shell bypass.

### 6. Contract and release coherence

Bump Heidi/MCP contract to `2.1.0`. The compact action count becomes 21. Compatibility metadata documents the workspace lifecycle addition and owner-full profile migration.

Centralize the compact tool-name inventory in MCP release/contract code so tests and release metadata derive their count from one exported list rather than independently hard-coding 20/21 in several places. CI still asserts that compatibility metadata equals the runtime-exported count.

### 7. Tests

CPTR tests cover:

- zero-workspace managed create;
- Git clone argv construction without shell execution;
- rejection of credential-bearing repository URLs and unsafe names;
- import of an existing directory;
- FDX warm-up success and non-fatal degradation;
- archive without file deletion;
- request/confirm deletion, expiry/mismatch, and refusal to delete imported paths outside the managed root;
- scope enforcement at router boundaries.

MCP tests cover:

- 21-tool compact contract;
- lifecycle schema/annotations;
- create/clone/import dispatch and cache invalidation;
- backend error normalization.

Installer/release tests cover standard versus owner-full scopes, legacy `full` aliasing, v2.1 compatibility metadata, and generated compact tool count.

## Acceptance criteria

1. Starting with zero workspaces, ChatGPT can call one Heidi MCP action to clone `https://github.com/heidi-dang/heidi-cli.git` and receive a new workspace ID.
2. The new workspace appears immediately in `cptr_workspaces` without waiting for cache expiry.
3. A Git workspace reports FDX readiness or a bounded non-fatal fallback status.
4. Standard profile can bootstrap workspaces but cannot delete managed workspace directories or run external commands.
5. Owner-full can use the existing explicitly opted-in external command/browser/SSH paths and can confirm managed workspace deletion.
6. No repository URL containing embedded credentials is accepted or returned.
7. Imported external directories can be archived but cannot be recursively deleted by the lifecycle API.
8. MCP, CPTR, installer, release-contract, typecheck, Rust tests, and repository hygiene CI are green.
9. Heidi/MCP version and compatibility contract report `2.1.0` and the compact tool count reported by runtime metadata.
