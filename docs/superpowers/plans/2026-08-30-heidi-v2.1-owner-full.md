# Heidi v2.1 Owner-Full Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Add zero-workspace bootstrap, owner-full capability profile, automatic FDX readiness, and a coherent 2.1.0 MCP/release contract.

**Architecture:** Add a dedicated CPTR workspace provisioning service and one versioned lifecycle endpoint, then expose it as a compact MCP gateway. Keep clone/create under a managed workspace root, treat external imports as register-only, warm FDX non-fatally, and preserve explicit authentication/confirmation boundaries for destructive actions.

**Tech Stack:** Python 3.12/FastAPI/SQLAlchemy, TypeScript/Node 22/MCP SDK/Zod, Rust FDX protocol 2, Bash installer, GitHub Actions.

**Spec:** `docs/superpowers/specs/2026-08-30-heidi-v2.1-owner-full-design.md`

## Global Constraints

- Heidi/MCP contract version: `2.1.0`.
- CPTR Control API remains `/api/control/v1`.
- CPTR and MCP remain authenticated; no raw credentials or absolute host paths in ChatGPT-visible responses.
- `standard` gains `workspace:provision`; `owner-full` adds `command:external` and `workspace:delete`; legacy `full` aliases to `owner-full`.
- Managed clone/create paths are confined below `CPTR_WORKSPACE_ROOT`, default `<CPTR_DATA_DIR>/workspaces`.
- Git clone uses argv execution, never shell interpolation.
- Embedded credentials in repository URLs are rejected.
- Imported external directories may be archived but not recursively deleted by workspace lifecycle.
- FDX warm-up failure is non-fatal and returns bounded fallback metadata.
- Destructive workspace deletion stays request/confirm two-step.
